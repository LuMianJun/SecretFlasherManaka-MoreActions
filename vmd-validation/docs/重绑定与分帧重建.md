# 重绑定与分帧重建（0.7.2）

0.7.1 的原游戏日志显示，每套骨架首次准备仍同步耗时约 1.5～1.7 秒。按帧安排整套构建没有分摊套内工作；读档又清空缓存，因此会再次出现长帧。0.7.2 将形状数据、辅助骨架和活角色引用分离。

- 读档/换场景时解除旧角色引用，保留不随场景销毁的辅助骨架。对新角色重新采集必要引用及形状快照，相同形状只重新绑定 49 个身体骨和当前表情网格，不重新创建求解节点或映射。
- 原生 ReAdjust 和 OnChangeBody 只请求重新核对数据，不直接证明体型已改变。等待原生缩放回调完成后比较绑定矩阵、Armature 局部变换和原生缩放包装节点的尺度，数据确实变化且没有对应缓存形状时才构建新结果。对比采用小浮点容差；纯世界位移或朝向变化不会导致重建。
- 绑定快照优先沿必要身体骨路径查找，明确处理原生 PlayerBoneScaleAdjuster 包装；优先使用身体/脸网格，所需数据收齐即停止。取消先前对整个角色所有 Transform 和服装绑定矩阵的无条件扫描。
- 快照采集和 Unity 节点创建使用可暂停的迭代步骤。主线程每帧最多推进 8 步，以 2ms 为调度预算；单次 Unity API 本身不能被中途抢占，因此预算不是对单个 API 的硬性耗时保证。首轮构建和真体型变更都走同一分步调度。
- 虚拟 MMD 拓扑与参考位置的数学计算使用托管 System.Numerics，在完成主线程快照后放到后台；配套 PMD 从已加载模板复制数据。后台不访问活 Transform 或创建 Unity 对象。
- 闲置缓存每种源骨架保留最多两种旧形状，避免长期切换体型导致无界增长。并发租用保持独立求解器；旧角色上的租约完成姿势恢复后才释放绑定。
- 播放仍等待当前目标验证/准备完成，可取消，不回退到点击时同步构建。直接 API/离线适配器保留同步入口；原游戏播放由 IPreparedActionSource 门控，使用分帧准备泵。

日志 `MMD_RIG_READY mode=rebind` 表示复用和重绑定；`mode=build` 表示首次或形状变化后的新建。`totalMs` 是跨帧等待与后台计算在内的总时间，`maxOperationMs` 是单个主线程步骤的最大耗时；都不能直接当作完整帧耗时。性能改进须由原游戏下一轮日志/体感验证。
